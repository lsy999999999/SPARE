# 新负载上的容量曲线、同配置消融与简单压力基线

2026-09-23，设计版。策略定义、窗口和矩阵先于新 GPU 结果确定。当前交付是实验设计与输入冻结；本文没有新增性能结论，也不表示完整 GPU 实验已经启动。

## 决策：主实验直接用 4090，先不让模拟器承担性能结论

本轮要回答三个问题：A 的收益是否跨容量存在；收益来自动态控制还是选了合适的小预算；复杂一点的物理 KV 判断是否真的胜过简单占用率规则。

采用已有 Qwen2.5-7B-Instruct、vLLM 0.9.2 V1、同步 eager 实机入口，复用计时、逐轮分配审计和恢复路径。当前 A 的 V1 语义已有实机验证；simulator 尚需对齐这些语义，用它替代主表会引入额外不确定性。本轮本机先完成输入冻结、策略逻辑和分配检查；GPU 提供容量曲线。模拟器与 GPU 的端到端对齐列为随后独立任务。

只读检查时，服务器 GPU **2、6、7 为可用 RTX 4090**；0、1、3 有其他进程，4、5 为已占用 L20。启动前再次查询，不能把利用率为 0 但驻留模型的卡视为空闲。利用所有当时空闲且通过检查的 4090；本设计按三张估算。

## 一、数据怎么换：新日期的连续请求，原始输出长度

用本地已有 Azure 一周 code/conversation 长度日志。时间均为 **UTC**，不将其解释成用户所在地的早晚周期。每个预定分钟取开头连续 N 条请求，保留输入长度、输出长度和原始到达时间配对，不按长度或 A 的收益筛选。

继续使用长度重放：GPU 执行真实模型计算，但输入 token 使用统一的合成占位序列，输出通过 ignore_eos 和指定 token 数重放日志长度。它不是原始文本的语义生成评测。已知终长只供负载执行器控制完成时间，不能作为在线 A 或压力规则的输入。

| 用途 | code 起始分钟 | conversation 起始分钟 | 每窗口请求数 |
| --- | --- | --- | ---: |
| 简单基线调参 | 2024-05-11 08:00 | 2024-05-13 08:00 | 32 |
| GPU A/A 与运行时间校准 | 2024-05-11 20:00 | 2024-05-13 20:00 | 32 |
| 测试窗口 0 | 2024-05-12 08:00 | 2024-05-14 08:00 | 64 |
| 测试窗口 1 | 2024-05-14 14:00 | 2024-05-16 14:00 | 64 |
| 测试窗口 2 | 2024-05-16 20:00 | 2024-05-18 20:00 | 64 |

共 2 个调参、2 个校准、6 个测试窗口。相比上一轮 code 的 5 月 13 日、conversation 的 5 月 15 日比较窗口，测试日期已换；新窗口也避开此前数据清单内的 train/validation/test 分钟。仍是同一数据集的新时间窗口，不能叫新数据集，也不能凭这六个窗口证明厂商每日分布稳定。

每个窗口生成两种到达方式，**输出长度均为原值，不乘 4**：

- `original`：保留相邻到达时间差，只把第一个请求的时间平移到 0。准确名称是“自然到达的 64 请求窗口”，不是长时间稳态服务。
- `burst20ms`：相对时间线等比例压到 20 毫秒，保持请求顺序和长短配对。这是合成突发压力测试，单独报告。

先核验源文件哈希、请求 ID、时间顺序、上下文范围及最小容量下单请求可行性。如果预定窗口不可行，记录不可行原因，不能默默丢长请求或按效果找替代窗口。完整历史重叠审计在正式执行前进行，输入生成器当前只检查前述数据清单。

## 二、四个核心方法：把问题一次分清

所有方法固定 SRP 顺序、V1 引擎、KV 分配器、恢复逻辑及并发上限 32。A 和同配置 SRP 的基础 `(总预算, 分块, 并发)` 在所有容量、负载、来源上统一为 **(1024, 256, 32)**。这是上一轮已使用的配置，不从新测试结果挑选；A 的候选、次序、7/256 门槛及保护条件原封不动。

| 方法 | 精确定义 | 要回答什么 |
| --- | --- | --- |
| `srp_matched` | 固定 (1024,256,32) | 同一静态配置下，加上 A 是否有净收益？ |
| `a_frozen` | 当前冻结 A，按本轮物理 KV 增量选候选 | 本轮研究对象 |
| `fixed_small_dev` | 每轮使用同一个开发集选定预算 B，分块 min(B,256)，并发 32 | 是不是始终用小预算就够了？ |
| `occupancy_dev` | 调度前 KV 占用率 ≥ τ 时预算用 512，否则用 1024；分块 256、并发 32 不变 | 简单看“缓存快满了”是否就够了？ |

占用率明确为 `1 - free_blocks / usable_blocks`，其中 usable_blocks 不含 V1 保留 null block。压力规则每轮独立判断，不增加滞回、预测器、搜索或额外完成保护；它读取调度前状态，随后调用同一个原生调度器。缩预算不等于直接驱逐请求，也不修改已提交的分配。

调参仅给两种新增简单基线：固定预算候选 **128、256、512、1024**，占用率阈值候选 **0.70、0.80、0.90、0.95**。固定预算列表包含与压力规则低档完全相同的 (512,256,32)，避免遗漏最直接的静态对照。

每个候选在两个调参窗口、768/1536/7445 三种容量、两种到达上各跑一次：`2 × 3 × 2 × (4+4) = 96` 次。以同点固定预算 1024 的 TTFT 为参照，计算各点 TTFT 比值的等权均值，选全局一个 B 和全局一个 τ；不按容量、来源或测试窗口分别选。完全同分时，固定规则选较大 B，压力规则选较高 τ。任一开发点超时的候选不参与选择；没有完整候选就报告该基线的开发失败，不能换一套未声明的规则补进去。

这里 A 是预先固定的现有方法，两种新基线各有四候选调参额度；不是所有方法都重新调参的 SOTA 排名。更全面的各方法独立调参可以作为后续实验。

## 三、容量曲线：先看最重要的一张图

容量取 **768、1024、1536、2048、4096、7445 blocks**，block size = 16 token。记录配置总块数和实际可用块数，null block 单独记账。最小容量下先检查单请求的保守峰值需求不超过可用容量。7445 是上一轮同硬件的完整配置，本轮仍需测量核实能否使用，不冒充自动测得的新容量。

核心矩阵为 `6 容量 × 2 到达 × 6 窗口 × 4 方法 × 2 重复 = 576` 次。先运行所有点的第一遍 288 次，检查失败和完整性；再执行原定第二遍，不根据第一遍收益删点、换参数或放弃负例。

主图横轴为 KV 容量，纵轴为相对同配置 SRP 的平均 TTFT 改善；自然到达与突发分图，code 与 conversation 分面或明确分组。配套画抢占/重算、干预比例、吞吐和尾延迟，报告各窗口数据。

**提前写下一个重要边界：当前 A 在大容量处可能“设计上就不触发”。** 在正常增量分配分支、预算 1024、最多 32 个请求的条件下，本轮新增 block 上界不超过 `ceil(1024/16)+32-1 = 95`；4096/7445 的增长门槛分别为 112/204。因此这两点主要检查不干预时的成本及与简单压力规则的差异。若观察到超出此界，先核查分配假设和实现。不能看到 A 无干预，就据此声称大容量不需要调度优化。

本轮不改 A 的门槛“救活”高容量点；如结果提示按总容量归一化限制了适用范围，那就是本轮应揭示的设计边界。后续新规则需要新开发和确认数据。

## 四、只做会改变行为的消融

预先固定在 **768、1536、2048** 三个容量补三种方法；复用核心矩阵的同配置 SRP 和 A，不重复算成新独立数据。

| 消融方法 | 改什么，其他保持一致 | 检验内容 |
| --- | --- | --- |
| `a_no_finish_guard` | 去掉“基准本轮能出首 token 的请求不得减配”，保留 decode 保护、候选、节约门槛 | 完成保护是否减少了错误延后，代价是否值得？ |
| `a_any_positive_saving` | 本轮增长触发及候选节约门槛都从 ceil(total×7/256) 改为 1 block；其他不变 | 必须省下“足够多”，还是只要省一点就值得？ |
| `occupancy_finish_guard` | 使用已选定的同一 τ 和同一减半预算；候选正常分配可行且保留基准 decode/首 token 分配才执行，否则回基准 | 简单占用率加保护，是否已经足以替代 A？ |

新增 `3 容量 × 2 到达 × 6 窗口 × 3 方法 × 2 重复 = 216` 次。记录各保护条件拒绝候选的次数和被延后请求的实际后续等待，不能只凭总体均值归因。

不单独做“去掉最初增长检查”：保留同样的节约门槛时，它可能只增加无效候选计算而不改变动作。不把“去掉 decode 保护”列为主要行为消融：当前 decode 优先且最小候选预算大于并发上限，正常分支下这项保护很可能自动满足。先用状态级差分确认；没有动作差异就报告冗余，不包装成性能贡献。

另外在 **768、7445** 跑 `a_shadow`：计算 A 的选择但实际执行 SRP，用于量化决策开销。新增 `2 × 2 × 6 × 2 = 48` 次。它能辅助解释开销，不把 A-shadow 差值当成严格可加的因果分解。

## 五、怎么用三张卡跑得快，又不把卡的差异算成收益

比较的单位是“完整请求窗口”。code 0/1/2 分别固定 GPU 2/6/7；conversation 0/1/2 分别固定 GPU 6/7/2。**同一窗口的所有容量、方法和重复均在同一物理 GPU 上执行。** 每张卡一个工作进程，按容量复用引擎，统一预热；不同卡并行不同窗口。

同一 `(窗口, 容量, 到达方式)` 的全部比较方法一起排入任务，轮换方法顺序，第二次反向；核心、消融和 shadow 按其适用点共同交错，不能隔一天才单独补一个对照。调参的 code 窗口固定 GPU 2，conversation 窗口固定 GPU 6，所有候选同卡配对。全局有调参屏障：两种基线选定并保存哈希后，才允许跑测试窗口。

沿用已验证过的每 GPU 三个 CPU 核心分配作为起点，启动前检查拓扑和负载。每次记录 GPU UUID、CPU affinity、环境/模型/代码/trace 哈希、温度及资源占用。空闲检查、每 GPU 排他锁和总调度锁避免重复启动；若别人的作业进入则保存现场、暂停该卡队列，不结束无关进程。

新增空闲卡时，先完成相同验证，再把**尚未开始**的完整窗口转移到它；不能把同一窗口的一半方法或第二次重复迁过去。两遍之间卡不可用则等候或完整重跑该窗口并保留旧记录，不混卡拼接结果。L20 若另做扩展，应独立标注和汇总。

执行顺序：

1. 本机核对冻结 A 的文件哈希；验证新规则边界和与原生 V1 分配的差分，特别是 null block、抢占恢复、首 token、shadow 等价性。不能把模拟器自己的分配判断当成原生分配验证。
2. 三张卡各做 7 种核心/消融方法的小型运行，以及 64/256-token 两种分块的物理分配检查：共 **27** 次。shadow 的执行等价另在差分测试验证。
3. 每卡在 768/7445、两个校准窗口上各做 SRP 三次：共 **36** 次 A/A。平均 TTFT 和总运行时间的组内极差/均值均需 ≤5%；若失败，保留记录并先处理环境。最多一次有记录的环境修复后整组重跑，仍失败则该卡不进入比较，不能反复抽样直到过线。
4. 完成 **96** 次基线调参，冻结选择；再执行已排定的核心、消融和 shadow 任务。先输出核心第一遍的描述性中间结果，最终结论等待两遍完成。
5. 从原始逐请求时间和逐轮记录独立重算指标，检查任务数、失败数、输入一致性、策略保护、KV 上界和文件哈希，再生成曲线和中文报告。

共计划 **999 次运行**：27 smoke + 36 A/A + 96 调参 + 576 核心 + 216 消融 + 48 shadow。不含引擎预热、失败后的重启和有记录的 A/A 修复。任一运行达到 300 秒截止，就记超时和完成比例、终止该运行并换新引擎继续其他任务；不得只平均成功请求或默默删除失败方法。

上一轮 96 次比较的运行时间均值约 69.85 秒，中位数约 49.58 秒；按旧均值粗算，999 次在三卡均衡运行约 **6.5 小时纯运行时间**，另有环境检查、预热、加载与调参屏障。新主负载不再将输出乘 4，可能更快；极端压力和超时也可能更慢。先用开发/校准运行更新 ETA，不用测试收益决定是否继续。全部触及 300 秒时约需 27.8 小时纯运行时间，不能承诺几分钟完成。

## 六、报告哪些指标，怎么判断结果

主指标为每窗口 mean TTFT。以相同窗口、相同容量/到达和同卡的运行配对，先平均技术重复，再报告窗口收益；全体均值按来源等权。保留毫秒差值和相对百分比，避免只有单个百分数。

副指标包括 p95 TTFT、平均/尾部输出间隔、E2E、长输入请求的等待和最大退化、完成率、吞吐、抢占次数、重算 token、干预率、候选检查数、决策平均/p95/累计耗时。总体吞吐与“相同响应要求下的有效吞吐”是不同问题，本轮先报告前者；SLO 门槛和长时间持续负载留待后续预定实验，不能看结果后挑一个 A 刚好赢的 SLO。

两个技术重复不是两个新负载。六个时间窗口仍偏少；置信区间只作探索性描述，按来源分层、以窗口为重采样单位，跨容量和两种到达变换保持窗口关联，同时展示六个配对点。不能把 64 个请求、两个重复、六个容量当作大量独立样本来证明显著性。

| 观察到的结果 | 下一步怎么处理 |
| --- | --- |
| A 在相邻多个压力点胜过 SRP、固定小预算和占用率规则，且完成保护确实减少坏动作 | 进入更多日期/窗口与另一模型的独立确认，主线继续讲保护式动态预算 |
| 固定小预算与 A 相当或更好 | 当前证据不足以说明动态控制必要；分析 A 是否只是实现了一个偏小的平均预算 |
| 占用率规则或其加保护版本与 A 相当或更好 | 优先考虑更简单的机制，不能坚持物理增长搜索必不可少 |
| A 仅在单个容量点或某个窗口有效 | 收窄适用范围，继续诊断；不能写跨负载稳健提升 |
| TTFT 更低但长请求、输出间隔或完成时间明显退化 | 正面展示权衡，补预定 SLO 对照，再决定是否有部署价值 |
| 原始输出下没有收益，只有未来另设的输出×4压力测试有收益 | 结论限定在合成压力条件，不能回写成自然负载的普遍优势 |

“可继续推进”的判据是跨点一致的机制证据和可解释的代价，不是预先规定 A 必须赢多少。独立正式确认前可据开发证据改方法，但一旦利用本轮测试结果改规则，这六个窗口就成为开发数据，新版本需要新的留出集。

## 七、本轮之后，再决定扩展什么

容量曲线回答有限窗口在不同资源约束下的行为，仍不能替代固定完整容量下的持续到达率扫描。若核心机制成立，下一轮用新窗口在固定完整容量上扫描到达强度，观察 warmup、队列增长和稳态；如果冻结 A 因门槛根本不触发，就把这一限制如实写明，不能把缩小容量等同于真实线上峰值。

simulator 的下一步是用本轮开发实机测量校准，并留出测试窗口及容量点，检查相同策略的 TTFT、吞吐、恢复行为，尤其 A-SRP 差值及排序。未通过前，它用于状态分支检查和反例生成；通过后再用它扩展大矩阵。完整模拟器贡献和“每日分布拟合”均不塞进本轮，以免核心问题尚未验证就分散工作。

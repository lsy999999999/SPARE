# Conversation-only 突发后持续到达 GPU 复验协议

本批回答：在只使用 Conversation 请求长度的六个新时间窗口中，SPARE 的突发后持续到达效果是否仍然成立。设计发生在已看到六窗口混合批次结果之后，因此单独报告，不把它冒充预先设定的跨工作负载验证，也不从原批次删除 Code 负例。

从 Azure Conversation 2024-05-12 至 2024-05-17 每天 09:00 UTC 起，按原轨迹顺序取 128 个先前未用、符合输入>0、输出 1–512、总长≤8000 的请求。对所有既有 `artifacts/v1*`、`artifacts/www*` 输入档案及 `writing/www/experiments/inputs` 的 ID 做交集检查。只重放长度，不称为真实文本或生产到达过程。每窗口前 32 个请求在 t=0 到达，后 96 个以 5.25 req/s 持续到达，然后排空。

六窗口×768/2048/4096 blocks×SPARE/SRP/原生固定 256/原生固定 512×四重复，共 288 次正式测量；每场景两次 SPARE A/A。引擎、模型、参数、预热、顺序配对、指标、5% A/A 门槛、空闲 GPU 2/6 检查、失败整组最多两次重试、900 秒 episode 上限、12 小时整组 watchdog、72 小时全批截止及逐轮哈希审计，均与 2026-10-09 混合批次相同。所有正负结果保留，按场景先平均四重复，再按六个源窗口成组汇总。

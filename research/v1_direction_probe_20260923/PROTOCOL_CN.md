# 快速方向实验（2026-09-23）

目的：用少量原生 V1 CPU 分配实验判断多轮压力和候选力度是否值得继续；不做完整容量验证，不据此宣称 GPU TTFT 收益。4090 服务器当前 SSH 认证失败，本机 V1 0.9.2 CPU 调度器可用。

使用已有开发窗口 code_test0/conversation_test0，各 64 请求，容量 768/2048。全部在初始时刻到达，真实输出长度只用于环境终止请求，策略只收到当前 State。单位时钟为调度轮，既不复现自然到达，也不估计毫秒。所有方法保留原有 decode/本轮完成保护及原生恢复。原文件不修改。

第一批 10 方法 × 4 点 = 40 次确定性闭环：1-block、固定512、pressure_one、pressure_early（1/8）、pressure_min_delay、horizon4_first、horizon8_first、horizon4_min_delay、horizon4_risk、horizon8_risk。不作无意义的确定性重复。

- early 只降低单轮门槛，作为“新方法其实只是更早触发”的简单对照。
- min_delay 枚举原候选集合中全部可行且至少节约 1 block 的候选，选择本轮被延后首 token 前工作量最少者；平局按更大节约、原候选顺序。它刻意不要求消除风险，用于探查保守小幅减配的后果。
- horizon：从当前状态推进 4/8 轮。首轮用真实可行基础计划，后续用共同的基础预算和现有排序；假定已活跃请求继续输出，没有未来到达，也不假定完成释放。后续用无限空间的影子分配计算潜在新增需求，遵守并发和长度上限。需求超过当前可用 blocks 时触发。它是有偏的压力情景，不是已验证的预测器。
- risk：每个合格候选首轮只执行一次，后续恢复共同基础计划，比较整个短窗口累计需求相对空闲量的缺口。基础计划也参与排序，按缺口、延后 token、延后请求数、原顺序排序；没有严格降低风险就不干预。本实验专门检查这种风险优先选择是否过于保守或激进。

记录：完整完成率、首 token 等待轮数、抢占、重算、总轮数、延后量、候选分布、策略 CPU 时间、未触发且未来8轮内发生抢占的次数。后一项只描述本策略轨迹上的事件关系，不是反事实因果收益。

验证：旧方法动作哈希对齐上一轮 CPU 结果；新增候选每轮接受原生分配/保护断言；独立检查请求最终输出数、逐轮统计和输入/源码哈希。短窗口推演用不跨结束边界的原生状态轨迹做差分测试。

结果全部保留。若只得到负例，交付负例及下一步的缩小方向，不追加大规模参数搜索。E2E/TBT 本轮不进入目标；CPU 轮数也不能替代其 GPU 时间指标。
